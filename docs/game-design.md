# 遊戲設計草案

## 團隊共識草案

- 單人玩家扮演任務負責人，根據各組提案做決策並簽署放行。角色職責見[主線](story/main-story.md#角色)。多人原型的玩家分別擔任 PM 和部門代表，見[多人合作草案](multiplayer.md)。
- 系統工程是教學主線。每場審查都檢查當下的設計和證據是否足以往下走。證據不足時，玩家可以補分析、改設計或重測。結算要能從任務成果追溯到需求、決策與驗證結果。
- [NASA 資源與玩法調整提案](nasa-mission-design-notes.md)記錄可引用的段落與立方衛星試玩方向。

## 架構選型

採用 **React + TypeScript + Vite**，以 npm 管理套件，做成可靜態部署的網頁遊戲。第一版的任務內容隨程式打包，單人存檔使用瀏覽器的 `localStorage`。多人連線方案見[多人合作草案](multiplayer.md)。 [Vite 靜態部署](https://vite.dev/guide/static-deploy.html)

| 模組 | 負責內容 |
| --- | --- |
| 畫面 | 顯示目前階段、資源、組別回報與可用操作，把玩家動作送給規則。 |
| 遊戲規則 | 用純 TypeScript 函式更新單局狀態，由 React 的 `useReducer` 接到畫面。規則執行工作、扣資源、檢查需求和審查條件，並記錄判定原因。每局的種子決定事件抽選和每個風險項目的真相，連同玩家操作保存，方便重現同一局。 |
| 情境資料 | 每個任務一份具型別的 TypeScript 資料。任務定義初始工期、預算與需求。選項定義文案鍵、可用階段、前置條件及資源或設計的變動。事件定義何時可出現、發生時改變什麼。各任務共用判定方式。 |

畫面從同一套規則取得「還能做什麼」「為什麼這項不通過」和實際結算。回報使用固定文字模板，填入規則算出的需求名稱、門檻和結果。**可以用 LLM 在開發時草擬選項、事件文案和邊界案例**，由隊員確認工程因果和數值後提交。玩家遊玩時的選項、判定與回報都由瀏覽器執行。 [React useReducer](https://react.dev/reference/react/useReducer)

### 雙語

遊戲支援**繁體中文（`zh-TW`）與英文（`en`）**。大廳和任務中都可切換。首次依瀏覽器偏好選擇，兩種語言皆未匹配時採英文。手動選擇記在本機，切換時沿用當前進度。

介面、任務簡報、選項、事件、審查回報與結算共用文案鍵，分別查兩份具型別的 TypeScript 字典。遊戲規則和存檔使用固定識別碼、判定原因與數值，切換語言時由畫面重新套用文案。新增玩家看得到的內容時，在同一份 PR 補齊中英文。

### 選項怎麼組合

用共用狀態串起選項的後果。以立方衛星為例，酬載方案改變耗電，供電方案改變可用功率。兩組各有兩種選項，就能搭出四種配置。整合測試用同一條規則比較同時運作時的電力需求和供電上限，回報哪一項需求通過、哪一項有缺口。重測取得新證據，換供電方案或調整操作排程會改變實際結果。

## 使用者流程

**大廳 → 選擇任務 → 技術選型與可行性 → 詳細設計與定版 → 製造與子系統驗證 → 整合測試與發射審查 → 任務模擬 → 結算**

### 大廳與任務簡報

大廳選「開始新局」後，玩家從已解鎖的任務卡選一張。卡片顯示難度與預計遊玩時間，未解鎖的卡片顯示解鎖條件。任務簡報顯示目標、最低要求、額外目標、初始預算與交付期限。玩家確認後進入任務工作台。

立方衛星原型已有[單人自動存檔](../README.md#快速啟動)。跨局進度保留團隊聲望、解鎖進度及會觸發後續邀約的任務成果，見[整體主線與跨局成長](story/main-story.md)。

### 工作台與回合

工作台常駐顯示目前階段與三個取捨指標。

- **時間**顯示剩餘週數和交付期限。
- **經費**顯示剩餘可用額與目前方案的預估剩餘支出。
- **任務完成度**逐項顯示需求預估能否達標、是否已有驗證證據，以及任務操作後的實際成果。規劃時讓玩家看得出哪些最低要求還有缺口。

每回合代表 1 週，玩家從各組提案選一項主工作，例如分析、製造、測試或返工。比較方案時顯示時間、經費與受影響的需求，按「執行並推進一週」後結算。閱讀簡報、比較選項和送審可以隨時做。退回時顯示待補項目，補分析、重做或重測才消耗工期。

各任務有自己的交付期限，工期可跨階段挪用。下表的開發週數是遊戲內工期，遊玩時間則是從選任務到結算的首次試玩目標。

### 各階段怎麼玩

| 階段 | 玩家操作與離開條件 |
| --- | --- |
| 技術選型與可行性 | 先從組別提案選任務架構，確認各組負責哪些需求（MDR）。接著選要優先做的分析或原型測試。關鍵可行性門檻達標，其他已知風險有處理方案，就能通過初步設計審查（PDR）。 |
| 詳細設計與定版 | 確認元件、跨組介面與驗證方式。關鍵設計審查（CDR）通過後定版，才開始製造。之後變更要列出受影響的介面與驗證項目，支付返工成本並重測相關項目。 |
| 製造與子系統驗證 | 選哪一組先開工、哪一項先驗證。追蹤各組交件與測試結果。必要的子系統就緒後，就能進整合。 |
| 整合測試與發射審查 | 跑跨組測試，檢查整套系統能否完成操作。發現問題可根據報告調整設計或操作方式，再重測。必要條件有證據支持後，才能通過飛行準備審查（FRR）並進入任務模擬。 |

審查名稱與目的參考 NASA，工期和通過門檻是遊戲原型設定。 [NASA 審查準則](https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_7123_001D_&page_name=AppendixG)

### 難度與遊玩節奏

「極限方案」指能把某項任務表現往上推，但要多投入工期、經費或驗證工作的選項。各難度以可行的方案組合來調整。

| 任務 | 初始期限 | 首次遊玩目標 | 玩家會遇到的取捨 |
| --- | ---: | ---: | --- |
| 簡單／立方衛星 | 依搭載方式為 6 或 7 週 | 3–5 分鐘 | 基準方案可在第 4 週完成必做工作。追加儀器、早測、返工與重測共用交件前的餘裕。 |
| 中等／入軌火箭 | 12 週 | 8–12 分鐘 | 以一項極限方案搭配其餘穩健方案作為平衡基準。開局的預算可能容許兩項，若遇到經費削減，工作台會更新剩餘預算與預估支出，讓玩家比較該保留哪一項。 |
| 困難／登月計畫 | 26 週 | 約 30 分鐘 | 開局選資金合作、技術合作或自力完成。六項驗證工作都是選做，時間夠做的錢不一定夠，玩家決定驗證投在哪裡，再帶著沒驗證的項目飛。政府要求提前交付、合作方退出等事件每局抽到的不同。飛行分七步，出狀況時用推進劑餘裕、經費和月面時段應對。 |

登月計畫要有至少兩條可通關的路線供試玩，例如用預付款支應自主研發，或用合作方的技術支援縮短關鍵工作。合作方式要能影響後面的整合選項，每次主要危機都讓玩家選擇要用什麼資源解決。通過飛行準備審查後，模擬分成發射、地球軌道檢查、月球轉移、進入月球軌道、下降、月面第一天、月夜七步，讓玩家看到前面保下來的能力各在哪一步派上用場。故事線、事件池和結局矩陣見[登月計畫分支](story/lunar-mission.md)，取材的真實任務見[事件表](story/lunar-history.md)。

**合作研發**會占用一個或多個主工作回合，這段時間主線少做相應的工作。合約在接受前列明所需週數、回報與取得時點。預付款能先補經費，里程碑款要等合作交件，技術支援則可縮短指定的研發或驗證工作。玩家依當前缺口判斷接案能否趕在主線需要前帶來幫助。

### 突發事件與測試結果

工程風險的規則是**驗證降低的是不確定性，不是失敗機率**。測試不會改變硬體，只會改變玩家對硬體的了解。每個風險項目的真相在開局就用種子抽好，玩家看不到。驗證是花工期和經費買資訊。飛行時不另外擲骰，結果由開局抽好的真相決定。共用規則在 [`src/game/risk.ts`](../src/game/risk.ts)。本節的百分比和範圍都是**遊戲設定**，不是 NASA 的數字。

真相有兩種。

- **隱藏數值。** 例如上面級實際運載能力和分析值的差距、酬載介面的實測質量、月球轉移的修正量。玩家只看得到範圍，新設計的範圍比沿用設計寬。每升一級驗證，範圍對半縮小，端到端測試揭曉真實值。設計餘裕蓋不住的那一段，就是玩家此刻認知的風險。
- **有沒有缺陷。** 例如降落時序、地面資料鏈。開局帶缺陷的機率是沿用設計 20%、新設計 40%。有缺陷的項目飛到那一段就會出問題。

驗證等級對應 NASA 系統工程手冊的驗證方法。每個項目逐級往上驗，每一級各有工期和經費，越後面越貴。各級的差別是**偵測能力**：缺陷存在時抓得到的機率。抓到或漏掉也在開局用種子決定，深的測試抓得到淺的測試抓到的所有缺陷。 [NASA 系統工程手冊 §5.3](https://www.nasa.gov/reference/5-3-product-verification/)

| 驗證等級 | 抓得到缺陷的機率 | 通過後的認知：沿用設計 | 通過後的認知：新設計 | 隱藏數值的已知範圍 |
| --- | ---: | ---: | ---: | --- |
| 沒驗證 | — | 20% | 40% | 整段起始範圍 |
| 分析 | 50% | 11% | 25% | 縮成一半 |
| 單元測試 | 85% | 4% | 9% | 再縮成一半 |
| 端到端測試 | 97% | 1% | 2% | 揭曉真實值 |

「通過後的認知」用貝氏定理算，不是另外訂的數字。例：新設計做分析且通過，還藏著缺陷的機率 ＝ 0.4 × 0.5 ÷（0.4 × 0.5 ＋ 0.6）＝ 25%。畫面上的百分比都是「玩家此刻的認知」。

測試有四種結果，遊戲都會出現。

| 情況 | 發生什麼 |
| --- | --- |
| 壞消息 | 測試回報有問題。玩家要選：**修**（再花工期和經費，修完那一項就沒問題）、**換設計**，或**明知有問題照飛**。測出問題卻沒有資源修，是一種輸法。 |
| 好消息 | 範圍縮小後，餘裕比保守估計多。玩家可以把原本留著的資源拿去用，例如省下輕量化零件或更深的測試。 |
| 白花 | 真相本來就沒問題，測試只是確認。通過後認知的風險下降，硬體和沒測時一樣。 |
| 漏掉 | 缺陷存在，但這一級沒抓到。通過不代表沒問題。 |

- 沒有任何一級抓得到所有缺陷，所以測試通過後認知的風險不會歸零。只有修好的缺陷和已揭曉的數值是確定的。
- 設計選項決定用哪一欄。新構型和高性能選項用「新設計」。
- 失敗分**降級**和**致命**。降級後任務繼續，能力變差，玩家用剩下的資源應對。致命則任務在那一段結束。每一章最多兩個致命項目，都列在工作台上。
- **備援**不改變真相。它把那一項的致命失敗變成降級。買備援和買驗證是兩種投資。
- 全部驗到最高級會讓工期或經費不夠送審。驗得越深，也越可能在沒有餘裕的時候才測出問題。
- **外部事件**是從事件池抽的，例如經費削減、供應延誤、交期提前。驗證不影響它。事件畫面列出變動前後的剩餘資源，再讓玩家回工作台改方案、重排工作或放棄額外目標。

NASA 把風險描述成情境、發生可能性、後果三者的組合，評估可能性和後果時要納入不確定性。不確定性的定義是「知識不完整的狀態」。風險處置包含接受、減輕、研究等選項，接受風險的決定要連同理由留下紀錄並由負責人簽署。遊戲的「認知的風險＋後果輕重」和 FRR 的「接受風險」對應這套做法。 [NASA 系統工程手冊 §6.4](https://www.nasa.gov/reference/6-4-technical-risk-management/) · [NPR 8000.4C 附錄 A](https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_8000_004C_&page_name=AppendixA) · [NPR 8000.4C 第 3 章](https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_8000_004C_&page_name=Chapter3)

**可重現。** 每局有一個種子。每個風險項目用「種子＋項目 ID」導出自己的真相和各級測試會不會抓到，所以多做一項工作、換一個操作順序，都不會改變另一項的結果。同一個種子加同樣的操作會得到完全相同的一局，測試結果和飛行結果也一定一致。種子、測出的問題和每個項目飛行時的結果都寫進單局紀錄。

**玩家看得到的資訊。**

- 每個風險項目目前認知的風險或數值範圍、驗證等級、後果是降級還是致命。
- 升一級要花多少工期和經費，以及通過的話認知會變成多少。
- 整趟任務的預估成功率，分成「完成最低要求」和「不發生致命失敗」。預估用玩家的認知計算。
- 失敗後的結算指出是哪一項出問題、玩家當時認知的風險是多少，以及下一級驗證要花多少、當初做了會測出來還是會漏掉。
- **FRR 接受風險。** 送審時，認知的風險高於 5% 的項目要由玩家簽字，包含已經測出問題但選擇不修的項目。畫面列出該項的百分比和後果，簽字後帶著它飛，並寫進團隊履歷。已知一定會致命的設計不能簽字放行。

### 任務模擬與結算

通過飛行準備審查後，以任務模擬判定成果。立方衛星用一次簡短操作收尾，較長的任務可拆成數個關鍵操作。模擬走到每個風險項目所在的那一段時，才揭曉開局抽好的真相。期限當週的工作完成後仍可送審。若審查未通過且工期已用完，或預算不足以繼續必要工作，玩家進入「未發射」結算。

- **花了多少**：原始與調整後預算與期限、實際支出、使用週數。
- **做到哪裡**：最後通過的審查、已完成與未完成的工作、是否發射。
- **達成什麼**：逐項顯示需求門檻、驗證證據、任務中的實際成果。未進入任務模擬的項目標為「尚無任務結果」。列出一兩個影響最大的決策。有項目失敗時，寫明是哪一項、玩家當時認知的風險，以及下一級驗證的花費和它會不會測出問題。提供「重玩同一任務」和「回大廳選任務」。

## 原型驗收規劃與待討論

1. **立方衛星先可玩。** 先做酬載、供電兩個決策點，各提供穩健與高性能方案，再加一個能補救的整合問題。依[單人試玩指南](development.md#單人試玩)驗收各條路徑，確認結算能指出是哪個選擇造成缺口。兩種語言各從大廳玩到結算一次，另確認任務中切換後的進度、動態回報與版面。
2. **入軌火箭沿用流程。** 換任務需求與選項，先加一張固定觸發的砍預算事件，驗證兩項高性能方案如何縮到一項。固定情境跑通後再加入隨機觸發。
3. **登月計畫擴充合作。** 先做兩條合作路線與一個交期提前事件，確認兩條路都能滿足最低需求。記錄各任務的首次結算用時。

團隊再決定各任務的具體交付成果、組別、正式審查節點、選項成本、驗證門檻，以及事件與合作案的數值。
